01 El problema: un endpoint público sin límites

Un endpoint público acepta cualquier cantidad de peticiones. Un cliente mal comportado, un script de scraping o un ataque de fuerza bruta pueden disparar miles de requests por segundo: la base de datos se satura, la API responde lento para todos, y el costo del servidor se dispara. Sin límites, el servicio es víctima de sus propios usuarios.

Uso normal

¿Quiénes abusan del endpoint?

  • Ráfagas (burst) — un cliente dispara miles de requests en segundos: retries agresivos, webhooks mal configurados, procesos duplicados.
  • Scraping — bots que recorren el endpoint para copiar datos; consumen recursos sin aportar usuarios reales.
  • Fuerza bruta — intentos repetidos contra endpoints sensibles (login, recuperación de cuenta) hasta acertar.
  • Saturación — el efecto acumulado: la base de datos se satura, la API degrada su latencia para todos y el costo del servidor sube.

El flujo del abuso

1 · peticiones ilimitadas→ 2 · DB y CPU saturados→ 3 · latencia para todos→ 4 · costo del servidor ↑

El rate limiting corta este flujo en el paso 1: permitir un máximo de peticiones por ventana de tiempo (p. ej. 100 requests por minuto) y responder con 429 Too Many Requests cuando se excede.

La pregunta del laboratorio: "100 por minuto" se puede implementar de varias formas, y cada una se comporta distinto bajo ráfagas. ¿Cuenta ventanas fijas de calendario? ¿Ventanas deslizantes continuas? ¿Un balde de tokens que se recarga con el tiempo? La elección cambia qué tan estricto es el límite, cuánta memoria usa, y cómo se siente para el usuario.

02 Los 3 algoritmos clásicos

Los tres implementan el mismo límite (100 req/min), pero con reglas distintas. Cada uno tiene una simulación interactiva que muestra su comportamiento bajo ráfagas — presione ▶ Ejecutar simulación en cada tarjeta.

(a) Fixed window ⚠️ SIMPLE PERO PUNZANTE

Cuenta en ventanas fijas de calendario (00:00–00:01, 00:01–00:02, …): un contador por ventana que se reinicia cuando empieza la siguiente. Memoria mínima (un contador + el inicio de la ventana), cero poda, trivial de implementar. Su debilidad conocida es la "carrera de límites": en el borde entre dos ventanas, un cliente puede disparar el doble del límite sin ser bloqueado — 100 al final de una ventana + 100 al inicio de la siguiente = 200 pasan.

límite100 por ventanaborde ×2
esquema (TypeScript ilustrativo)
1// Fixed window: windowStart = floor(now / windowMs) * windowMs
2export function createFixedWindow(clock: Now, opts: { limit: number; windowMs: number }) {
3 let count = 0;
4 let windowStart = Math.floor(clock() / opts.windowMs) * opts.windowMs;
5 return {
6 allow() {
7 const now = clock();
8 const start = Math.floor(now / opts.windowMs) * opts.windowMs;
9 if (start !== windowStart) { count = 0; windowStart = start; }
10 if (count >= opts.limit) return false;
11 count += 1; return true;
12 },
13 };
14}

  4. Resultado: 200 admitidas en ~1 segundo de tiempo real. El límite de 100/min se duplicó en el borde.
⚠️ La carrera de límites
El fixed window es simple y barato (memoria mínima), pero el borde entre ventanas es permeable: el límite se mide por tramos fijos de calendario, no por ningún intervalo real de 60 segundos. Un cliente que conoce el patrón puede duplicar su cuota.

(b) Sliding window ✅ CIERRA EL AGUJERO

Mantiene un log de timestamps de las peticiones admitidas y rechaza si hay ≥ 100 entradas en cualquier intervalo de 60 s (now−60000, now]. Al deslizar la ventana sobre el tiempo real, el límite aplica a cualquier intervalo de 60 segundos, no a tramos fijos — cierra el agujero del fixed window. El costo: más estado (el log crece con el tráfico y hay que podar entradas viejas en cada allow()).

esquema (TypeScript ilustrativo)
1// Sliding window (log de timestamps) con poda en allow()
2export function createSlidingWindow(clock: Now, opts: { limit: number; windowMs: number }) {
3 const timestamps: number[] = [];
4 return {
5 allow() {
6 const now = clock();
7 while (timestamps.length > 0 && timestamps[0] <= now - opts.windowMs) timestamps.shift();
8 if (timestamps.length >= opts.limit) return false;
9 timestamps.push(now); return true;
10 },
11 };
12}

El mismo patrón de ráfaga, ahora con ventana deslizante: en t=60 s el intervalo (0, 60000] todavía contiene las 100 del final de W0. Presione ▶ Ejecutar simulación.
  1. Las 100 requests del final de la ventana anterior entran al log (t=59,5–60 s).
  2. En t=60,0 s llega la primera request "de la ventana nueva": el intervalo (0, 60000] ya contiene 100 entradas → se rechaza con 429. En fixed window esta misma request habría pasado.
  3. Las siguientes 99 requests también se rechazan: el log sigue con ≥ 100 entradas en los últimos 60 s.

✅ Cualquier intervalo de 60 s
El sliding window aplica el límite a todo intervalo deslizante: el agujero del borde desaparece. El compromiso es memoria vs. exactitud: el log crece con el tráfico y la poda cuesta CPU por request. (Existen aproximaciones por precision sets para recortar memoria, a costa de exactitud — se documentan en la guía.)

(c) Token bucket ✅ RÁFAGAS CONTROLADAS

Un balde con capacidad 100 tokens que se recarga a una tasa fija (rate = 100/60 ≈ 1,67 tokens/s). Cada petición consume 1 token; se admite si hay ≥ 1. Permite picos cortos (ráfagas de hasta el tamaño del balde) mientras la tasa promedio se mantiene dentro del límite. El refill usa float: los tokens se acumulan fraccionados y se comparan con ≥ 1. Es el más flexible de los tres.

capacidad100 · refill 100/60 t/sráfaga = capacity
esquema (TypeScript ilustrativo)
1// Token bucket: refill float con clamp y comparación >= 1
2export function createTokenBucket(clock: Now, opts: { capacity: number; refillPerMs: number }) {
3 let tokens = opts.capacity;
4 let last = clock();
5 return {
6 allow() {
7 const now = clock();
8 const delta = now - last; last = now;
9 tokens = Math.min(opts.capacity, tokens + delta * opts.refillPerMs);
10 if (tokens < 1) return false;
11 tokens -= 1; return true;
12 },
13 };
14}

Dos fases: ráfaga corta (30 requests, todas pasan) y ráfaga sostenida (120 requests: el balde se vacía y empieza el 429). Presione ▶ Ejecutar simulación.
  1. Ráfaga corta: el balde está lleno (100 tokens) → 30 requests pasan todas; el balde queda en 70. El refill casi no se nota en segundos.
  2. Ráfaga sostenida: 100 requests pasan (el balde se vacía a 0) → las siguientes se rechazan con 429 hasta que el refill acumule tokens.
  3. Refill: a 1,67 tokens/s, en ~6 s se acumulan ~10 tokens → las próximas ~10 requests pasan, y así sucesivamente.
  4. Resultado: la tasa promedio se mantiene en 100/min mientras los picos usan el "crédito" acumulado del balde.
✅ El balde perdona picos, no abusos
El token bucket es el más flexible: una ráfaga de hasta la capacidad pasa sin fricción, pero el sostenido se corta cuando el balde se vacía. El refill float (comparar con ≥ 1) evita desperdiciar fracciones de token entre peticiones.

03 Headers y respuestas: el idioma del 429

Limitar del lado del servidor es solo una mitad: conviene comunicar el estado para que el cliente pueda comportarse bien. Dos familias de headers, con estatus normativo distinto:

429 Too Many Requests — RFC 6585 (obligatorio)

  • Retry-After — el 429 DEBE incluir este header (RFC 6585): cuántos segundos esperar antes de reintentar. Formato delay-seconds (entero).
  • Es el código correcto cuando el límite de peticiones se agotó; no es un error del cliente ni del servidor: es «vuelva más tarde».

X-RateLimit-* — de-facto (borrador)

  • X-RateLimit-Limit — el límite de la ventana (p. ej. 100).
  • X-RateLimit-Remaining — cuántas peticiones quedan (≥ 0, decreciente).
  • X-RateLimit-Reset — cuándo se restablece el límite, en epoch segundos.
  • No son obligatorios: son convención del borrador draft-ietf-httpapi-ratelimit-headers.
1HTTP/1.1 200 OK
2Content-Type: application/json
3X-RateLimit-Limit: 100
4X-RateLimit-Remaining: 42
5X-RateLimit-Reset: 1765217100 // epoch segundos
6// Remaining decrece con cada request: 99, 98, 97, …
1HTTP/1.1 429 Too Many Requests
2Content-Type: application/json
3Retry-After: 37 // RFC 6585: MUST en todo 429
4X-RateLimit-Limit: 100
5X-RateLimit-Remaining: 0
6X-RateLimit-Reset: 1765217100 // > ahora
7// Body (ejemplo): { "error": "rate_limit_exceeded", "retry_after": 37 }
RFC 6585 vs. borrador de headers. El 429 y su Retry-After son obligatorios (RFC 6585: el servidor que responde 429 MUST incluir Retry-After). Los X-RateLimit-* son una convención de-facto del borrador draft-ietf-httpapi-ratelimit-headers: casi todas las APIs los exponen, pero no son un estándar aprobado. En el laboratorio, toda respuesta (200 y 429) incluye los tres X-RateLimit-*; el Reset viaja en epoch segundos.

05 Las 5 hipótesis del README

Antes de correr los experimentos, el README plantea estas expectativas. Los experimentos existen para confirmarlas o desmentirlas con datos medidos — no para darles la razón por defecto.

H1

Fixed window es simple pero punzante

"En el borde entre dos ventanas, un cliente puede disparar el doble del límite sin ser bloqueado."

Ventanas fijas de calendario (00:00–00:01, …): 100 al final de una ventana + 100 al inicio de la siguiente = 200 pasan — la "carrera de límites".

Prueba: exp-01 · ráfaga cruzando el borde.
H2

Sliding window suaviza el borde

"Al deslizar la ventana sobre el tiempo real, el límite aplica a cualquier intervalo de 60 segundos."

Cierra el agujero del fixed window a costa de más estado y cómputo (o de aproximaciones por log/timestamps).

Prueba: exp-02 · el mismo patrón de ráfaga.
H3

Token bucket permite ráfagas controladas

"El bucket acumula tokens y se recarga a una tasa fija; permite picos cortos de hasta el tamaño del bucket."

La tasa promedio se mantiene dentro del límite mientras los picos usan el crédito acumulado. El más flexible de los tres.

Prueba: exp-03 · ráfaga corta vs. sostenida.
H4

Bajo ráfagas sostenidas, los tres bloquean igual de tarde

"Con 1000 requests en ráfaga, todos terminan rechazando ~el mismo total."

Pero con distinto patrón de éxitos/429 en el tiempo: el token bucket deja pasar una ráfaga inicial; el sliding window reparte de forma más pareja.

Prueba: exp-04 · comparativa bajo ráfaga (éxitos, 429, p95/p99).
H5

Los headers importan

"Un cliente que respeta Retry-After y X-RateLimit-Remaining se comporta mejor que uno ciego."

Sin headers, el 429 es solo un número que el cliente ignora; con ellos, el cliente puede autopausarse y reducir sus propios rechazos.

Prueba: exp-05 · cliente respetuoso vs. ciego contra api.ts.
